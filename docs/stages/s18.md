# S18 — Capstone: escala, isolamento e banco dedicado

- **Suite de testes:** `tests/p_18.spec.ts`
- **Tag:** `s18`
- **Status:** pendente

## Objetivo

Decidir com dados: o motor escala com N réplicas? Vale um banco dedicado?

## Incremento

- **N réplicas** do worker com `SKIP LOCKED`.
- **Advisory lock** para jobs singleton/reconciler.
- Comparar throughput/cauda com banco compartilhado vs. dois bancos (um para o
  motor).

## Queries prováveis

```sql
-- N réplicas disputando a mesma fila (mesmo claim do S7)
UPDATE job
SET status = 'running', locked_by = $1,
    locked_until = now() + interval '30 seconds'
WHERE id IN (
  SELECT id FROM job
  WHERE status = 'pending' AND run_at <= now()
  ORDER BY run_at
  FOR UPDATE SKIP LOCKED
  LIMIT $2
)
RETURNING *;

-- reconciler: só uma réplica roda (leader election)
SELECT pg_try_advisory_lock(42);

-- medir acúmulo da fila durante o teste de escala
SELECT count(*) FROM job WHERE status = 'pending';
SELECT count(*) FROM job WHERE status = 'running';
```

## O que a suite `p_18` deve validar

- Throughput **escala** com o número de réplicas (sem duplicar trabalho).
- Nenhum job fica perdido ou processado duas vezes sob N réplicas.
- O advisory lock garante **single-runner** para a tarefa singleton.
- Existem números para decidir isolamento (compartilhado vs. dedicado).

## O que observar no banco

- Throughput e cauda (p99) por número de réplicas.
- `pg_stat_activity` / conexões (liga com S17).
- Contenção no claim e crescimento de dead tuples sob alta concorrência (S5/S6).
- Custo/benefício de um **banco dedicado** ao motor vs. compartilhado.
