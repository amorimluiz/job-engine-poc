# S6 — Transações, isolamento, locks e deadlocks

- **Suite de testes:** `tests/p_06.spec.ts`
- **Tag:** `s06`
- **Status:** pendente

## Objetivo

Concorrência correta entre réplicas: bloquear sem travar, pular o que já está
travado e eleger líder para tarefas singleton.

## Incremento

- Scripts demonstrando `FOR UPDATE` esperando, `FOR UPDATE SKIP LOCKED` pulando,
  um deadlock intencional e um `pg_try_advisory_lock`.

## Queries prováveis

```sql
-- lock exclusivo de uma linha (bloqueia concorrente)
SELECT * FROM job WHERE id = $1 FOR UPDATE;

-- pular linhas travadas (base da fila em PG)
SELECT * FROM job
WHERE status = 'pending'
ORDER BY run_at
LIMIT 1
FOR UPDATE SKIP LOCKED;

-- eleição de líder / tarefa singleton (por réplica)
SELECT pg_try_advisory_lock(42);
SELECT pg_advisory_unlock(42);

-- inspecionar contenção
SELECT locktype, mode, granted, relation::regclass
FROM pg_locks WHERE relation = 'job'::regclass;
```

## O que a suite `p_06` deve validar

- Uma segunda sessão com `FOR UPDATE` **espera** pela primeira.
- Com `SKIP LOCKED`, a segunda sessão **não** espera e pega outra linha.
- O deadlock intencional é detectado pelo Postgres (erro `40P01`).
- `pg_try_advisory_lock` garante que só uma sessão detém o lock.

## O que observar no banco

- `pg_locks`: `mode`, `granted`, tempo de espera.
- `pg_stat_activity.wait_event_type = 'Lock'` quando há espera.
- Deadlocks aparecem no log e incrementam `pg_stat_database.deadlocks`.
