# S17 — Pooling e limites de conexão

- **Suite de testes:** `tests/p_17.spec.ts`
- **Tag:** `s17`
- **Status:** pendente

## Objetivo

Escalar workers sem esgotar conexões: cada processo abre um pool, e o banco tem
`max_connections`. Dimensionar pool ≠ dimensionar fila.

## Incremento

- Subir **PgBouncer** (descomentar no `docker-compose.yml`), transaction pooling.
- Apontar o PoC para ele.
- Medir com `max_connections` baixo e 2+ réplicas do worker.

## Queries prováveis

```sql
-- quantas conexões o banco permite/usou
SHOW max_connections;
SELECT count(*) FROM pg_stat_activity WHERE datname = 'job_engine';
SELECT state, count(*) FROM pg_stat_activity GROUP BY state;

-- conexões ociosas em transação (o que o PgBouncer multiplexa)
SELECT pid, state, query_start FROM pg_stat_activity
WHERE state = 'idle in transaction';
```

## O que a suite `p_17` deve validar

- Sem PgBouncer e com muitas réplicas, o erro `too many connections` aparece.
- Com PgBouncer (transaction pooling), o número de conexões ao Postgres fica
  **estável** mesmo com mais workers.
- O claim do S7 continua correto através do pooling.

## O que observar

- `pg_stat_activity` (contagem por estado) via PgBouncer vs direto.
- `max_client_conn` / `default_pool_size` do PgBouncer.
- Atenção: transaction pooling **não** suporta tudo (ex.: advisory lock de
  sessão, prepared statements nomeados, `LISTEN`) — validar o que o motor usa.
