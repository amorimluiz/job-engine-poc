# S7 — Fila no Postgres: `SKIP LOCKED` + lease

- **Suite de testes:** `tests/p_07.spec.ts`
- **Tag:** `s07`
- **Status:** pendente

## Objetivo

O coração do motor: **claim atômico** de um lote de jobs sem duplicar trabalho e
com **lease** para recuperar job de worker morto.

## Incremento

- `claimJobs(limit, workerId)`: `FOR UPDATE SKIP LOCKED` + `UPDATE ... locked_until`.
- Worker processa e marca `succeeded`/`failed`.
- _Sweeper_ devolve leases vencidos.
- Rodar com **2 réplicas**.

## Queries prováveis

```sql
-- claim: pega um lote pendente/vencido e marca como running com lease
UPDATE job
SET status = 'running',
    locked_by = $1,
    locked_until = now() + interval '30 seconds',
    attempts = attempts + 1,
    updated_at = now()
WHERE id IN (
  SELECT id FROM job
  WHERE status = 'pending' AND run_at <= now()
  ORDER BY run_at
  FOR UPDATE SKIP LOCKED
  LIMIT $2
)
RETURNING *;

-- concluir com transição condicional (só se ainda for meu)
UPDATE job
SET status = 'succeeded', locked_by = NULL, locked_until = NULL, updated_at = now()
WHERE id = $1 AND locked_by = $2 AND status = 'running';

-- falhar
UPDATE job
SET status = 'failed', locked_by = NULL, locked_until = NULL, updated_at = now()
WHERE id = $1 AND locked_by = $2 AND status = 'running';

-- sweeper: devolve lease vencido
UPDATE job
SET status = 'pending', locked_by = NULL, locked_until = NULL, updated_at = now()
WHERE status = 'running' AND locked_until < now();
```

## O que a suite `p_07` deve validar

- Nenhum job processado **duas vezes** com 2 workers concorrentes.
- Job de worker "morto" volta a `pending` após o lease vencer.
- A transição de conclusão é **condicional** (worker que perdeu o lease não
  sobrescreve).
- `attempts` incrementa a cada claim.

## O que observar no banco

- `job.status`, `locked_by`, `locked_until` durante a execução.
- Índice `job(status, run_at)` (S2) faz o claim escalar com `SKIP LOCKED`.
- Long-running transactions degradam o claim (dead tuples / MVCC — ver S5).
