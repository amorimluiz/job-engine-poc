# S2 — Índices + EXPLAIN

- **Suite de testes:** `tests/p_02.spec.ts`
- **Tag:** `s02`
- **Status:** pendente

## Objetivo

O maior multiplicador de latência: trocar **Seq Scan por Index Scan/Bitmap** nas
consultas quentes do motor, e **provar** a diferença com `EXPLAIN`/`BUFFERS`.

## Incremento

Criar o mínimo de índices que serve as queries do S1, **sem** over-indexar:

```sql
-- 1) jobs de uma pipeline
CREATE INDEX job_pipeline_id_idx ON job (pipeline_id);

-- 2) jobs de uma pipeline por status
CREATE INDEX job_pipeline_status_idx ON job (pipeline_id, status);

-- 3) claim/scheduler: só a fatia pendente/falha
CREATE INDEX job_pending_run_at_idx
  ON job (status, run_at)
  WHERE status IN ('pending', 'failed');

-- 4) histórico de execuções
CREATE INDEX execution_job_started_idx ON execution (job_id, started_at);

-- 5) observabilidade da fila (contagem por status)
--     -- avaliar se (status) já é coberto pelo índice parcial acima
```

> Observação: o roadmap original citava `priority` na ordem das colunas, mas o
> campo foi removido no S1 (redundante com `step`). A ordem passa a ser
> `pipeline_id, status` (igualdade, igualdade) e `status, run_at`
> (igualdade, range/ordenação).

Habilitar estatísticas de query:

```sql
-- postgresql.conf: shared_preload_libraries = 'pg_stat_statements'  (restart)
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
```

## Queries prováveis

```sql
-- 1) por pipeline
SELECT * FROM job WHERE pipeline_id = $1;

-- 2) por pipeline + status
SELECT * FROM job WHERE pipeline_id = $1 AND status = 'pending';

-- 3) claim: igualdade (status) + range (run_at) + ordenação
SELECT * FROM job
WHERE status = 'pending' AND run_at <= now()
ORDER BY run_at
LIMIT 10;

-- 4) por pipeline + step
SELECT step, status FROM job WHERE pipeline_id = $1;

-- 5) histórico
SELECT * FROM execution WHERE job_id = $1 ORDER BY started_at DESC;
```

## O que a suite `p_02` deve validar

- Os índices existem (`pg_indexes`), inclusive o **parcial** com o predicado certo.
- `EXPLAIN` da query (1) deixa de ser `Seq Scan` e vira `Index Scan`/`Bitmap`.
- `EXPLAIN` da query (3) usa o índice parcial e evita o `Sort` (ou usa
  `Incremental Sort`).
- `pg_stat_statements` disponível; `total_exec_time` das queries cai vs. S1.
- Nenhum índice redundante criado (ex.: `(pipeline_id)` não é redundante
  enquanto `(pipeline_id, status)` também existir — avaliar).

## O que observar no banco

- `EXPLAIN (ANALYZE, BUFFERS)`: `shared read` cai de milhares para dezenas de
  páginas.
- `pg_stat_user_indexes` (`idx_scan`) para saber se o índice é realmente usado.
- Custo de escrita: cada índice extra pesa nos `INSERT`/`UPDATE` de `job.status`.
