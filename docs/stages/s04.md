# S4 — Padrões de query, N+1 e O(n²)

- **Suite de testes:** `tests/p_04.spec.ts`
- **Tag:** `s04`
- **Status:** pendente

## Objetivo

Matar custo **quadrático** e **N+1**. Motores que recomputam agregados a cada
evento degradam sem limite conforme o histórico cresce.

## Incremento

- Trocar N+1 por uma query com `JOIN`/`ANY`.
- **Keyset pagination** (cursor) no lugar de `OFFSET`.
- **Agregação incremental** (`total = total + $1`) no lugar de `SUM` do histórico.

## Queries prováveis

```sql
-- ANTES (N+1): uma query por job
SELECT * FROM execution WHERE job_id = $1;
SELECT * FROM execution WHERE job_id = $2;
-- ...

-- DEPOIS: uma query para todos
SELECT e.* FROM execution e
WHERE e.job_id = ANY($1::bigint[]);

-- ou via JOIN
SELECT j.id, e.status, e.finished_at
FROM job j
JOIN execution e ON e.job_id = j.id
WHERE j.pipeline_id = $1;

-- Paginação por OFFSET (ruim em volume)
SELECT * FROM job ORDER BY id LIMIT 50 OFFSET 1000000;

-- Keyset pagination (estável)
SELECT * FROM job
WHERE (run_at, id) > ($1, $2)
ORDER BY run_at, id
LIMIT 50;

-- Agregação incremental (contador) em vez de SUM do histórico a cada evento
UPDATE pipeline SET updated_at = now() WHERE id = $1; -- ou uma tabela de stats
UPDATE pipeline_stats SET executions = executions + 1 WHERE pipeline_id = $1;
```

## O que a suite `p_04` deve validar

- O número de queries por job é **constante**, não cresce com o histórico
  (medir com `pg_stat_statements.calls`).
- A paginação por keyset retorna a mesma página de forma estável sob inserções.
- O caminho incremental não faz `SUM` do histórico (plano sem `Aggregate` sobre
  tabela inteira).

## O que observar no banco

- `pg_stat_statements.calls` antes/depois (N+1 = muitas chamadas).
- `EXPLAIN` do `JOIN`/`ANY`: comparar `Nested Loop` com `loops` alto vs.
  `Hash Join`/`Index Scan`.
- `OFFSET` grande força varrer e descartar N linhas — o `actual rows` explode.
