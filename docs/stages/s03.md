# S3 — Migrations sem downtime

- **Suite de testes:** `tests/p_03.spec.ts`
- **Tag:** `s03`
- **Status:** pendente

## Objetivo

Conseguir **aplicar os índices do S2 em produção sem bloquear escrita**. Sem
isso, o ganho do S2 não chega ao ambiente real.

## Incremento

- Migration aditiva e reversível que cria índice com
  **`CREATE INDEX CONCURRENTLY`**, o que **não pode rodar dentro de transação**.
- No TypeORM, a migration precisa desabilitar a transação. Padrão:

```ts
export class AddJobIndexes1720000000000 implements MigrationInterface {
  transaction = false; // fundamental para CONCURRENTLY

  async up(q: QueryRunner) {
    await q.query(`CREATE INDEX CONCURRENTLY IF NOT EXISTS job_pending_run_at_idx
      ON job (status, run_at) WHERE status IN ('pending','failed')`);
  }
  async down(q: QueryRunner) {
    await q.query(`DROP INDEX CONCURRENTLY IF EXISTS job_pending_run_at_idx`);
  }
}
```

- Tratar falha de `CONCURRENTLY`: o índice fica `INVALID`; limpar e refazer.

## Queries prováveis

```sql
-- aplicar sem lock longo
CREATE INDEX CONCURRENTLY job_pending_run_at_idx
  ON job (status, run_at) WHERE status IN ('pending','failed');

-- verificar validade do índice (indisvalid = true)
SELECT c.relname, i.indisvalid, i.indisready
FROM pg_index i JOIN pg_class c ON c.oid = i.indexrelid
WHERE c.relname = 'job_pending_run_at_idx';

-- reverter
DROP INDEX CONCURRENTLY job_pending_run_at_idx;

-- limites de tempo para não travar sessões
SET lock_timeout = '5s';
SET statement_timeout = '30s';
```

## O que a suite `p_03` deve validar

- Migration aplica e reverte sem erro.
- `indisvalid = true` após aplicar.
- Se um índice `INVALID` existir, a suite falha (limpeza obrigatória).
- (Opcional) aplicar com carga concorrente sem bloquear escrita.

## O que observar no banco

- `pg_index.indisvalid` / `indisready`.
- `pg_locks` durante a criação (não deve haver `AccessExclusiveLock` na tabela).
- `pg_stat_progress_create_index` para acompanhar o progresso.
