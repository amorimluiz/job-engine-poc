# S14 — Semântica de entrega, outbox e idempotência

- **Suite de testes:** `tests/p_14.spec.ts`
- **Tag:** `s14`
- **Status:** pendente

## Objetivo

Conciliar o banco (fonte de verdade) com a fila, sem o "dual-write": gravar
estado + intenção na **mesma transação** e publicar depois.

## Incremento

- Na transação que cria a `execution`, gravar `outbox(payload, sent_at null,
  attempts)`.
- Um **drenador** publica e marca `sent_at`.
- Testar crash entre os dois passos.

## Queries prováveis

```sql
-- mesma transação: estado + intenção
BEGIN;
INSERT INTO execution (job_id, status, started_at) VALUES ($1, 'running', now());
INSERT INTO outbox (job_id, payload) VALUES ($1, $2);
COMMIT;

-- drenador: pega lote não enviado sem travar entre réplicas
SELECT * FROM outbox
WHERE sent_at IS NULL
ORDER BY id
LIMIT 100
FOR UPDATE SKIP LOCKED;

-- marca como enviado (at-least-once: pode reenviar se crashar antes)
UPDATE outbox SET sent_at = now(), attempts = attempts + 1 WHERE id = $1;

-- lag/idade do outbox (observabilidade, S15)
SELECT count(*) AS pending, min(created_at) AS oldest FROM outbox WHERE sent_at IS NULL;
```

## O que a suite `p_14` deve validar

- Crash simulado entre o `INSERT` e a publicação **não perde** (o outbox drena).
- Crash após publicar e antes de marcar `sent_at` **não duplica efeito**
  (por causa da dedup do S13).
- A intenção e o estado são atômicos (mesma transação).

## O que observar no banco

- `outbox.sent_at IS NULL` (pendentes) e `attempts`.
- Ordem de `id` no drain para preservar ordering quando necessário.
- Tamanho do outbox: sem retenção/limpeza ele cresce sem limite.
