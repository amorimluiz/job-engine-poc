- **Tag:** `s12`

## Objetivo

Falhar **sem hot-loop**: retry classificado, com backoff, e DLQ inspecionável
para mensagens envenenadas.

## Incremento

- Fila `jobs_retry` com `x-message-ttl` + dead-letter (`x-dead-letter-exchange`).
- Header `x-retry` com contador.
- `jobs_dlq` como sink.
- Backoff exponencial; classificar transitório vs poison.

## Queries prováveis

O retry é feito no broker (TTL + DLX). No banco, o estado do job registra a
tentativa:

```sql
-- registrar falha transitória (o retry em si acontece via TTL+DLX)
UPDATE job
SET status = 'pending', attempts = attempts + 1, updated_at = now()
WHERE id = $1 AND locked_by = $2;

-- registrar poison (esgotou tentativas) -> DLQ
UPDATE job
SET status = 'dead', updated_at = now()
WHERE id = $1 AND attempts >= $2;
```

```ts
// publicação no retry com TTL e contador
channel.publish('', 'jobs_retry', Buffer.from(body), {
  persistent: true,
  expiration: String(backoffMs),
  headers: { 'x-retry': attempt + 1 },
});
```

## O que a suite `p_12` deve validar

- Falha transitória **volta após o backoff** (não imediatamente).
- A tentativa incrementa e o backoff cresce.
- Poison message vai para a **DLQ sem loop** (não fica reenfileirando).
- Nada de `nack(requeue=true)` em loop.

## O que observar

- Management UI: profundidade de `jobs_retry` e `jobs_dlq`.
- `attempts` por job; tempo entre tentativas (deve crescer).
- Mensagens em `jobs_dlq` são inspecionáveis (não perdem o payload).
