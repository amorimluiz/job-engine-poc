# S9 — Event loop e concorrência no Node

- **Suite de testes:** `tests/p_09.spec.ts`
- **Tag:** `s09`
- **Status:** pendente

## Objetivo

Não travar o processo com trabalho **CPU-bound** e limitar a concorrência para
não puxar trabalho infinito.

## Incremento

- Trocar `for` sequencial por `p-limit(N)`.
- Adicionar tarefa CPU-bound fake e ver o event loop travar.
- Mover para `worker_threads` e ver o ganho.

## Queries prováveis

Pouca coisa de banco; o foco é o runtime. O worker chama o claim do S7 em
paralelo limitado:

```ts
// concorrência limitada
const limit = pLimit(CONCURRENCY);
await Promise.all(batch.map((job) => limit(() => processJob(job))));
```

```sql
-- o claim continua igual; o que muda é quantos rodam em paralelo no processo
UPDATE job SET status='running', locked_by=$1,
  locked_until = now() + interval '30 seconds'
WHERE id IN (
  SELECT id FROM job WHERE status='pending' AND run_at <= now()
  ORDER BY run_at FOR UPDATE SKIP LOCKED LIMIT $2
) RETURNING *;
```

## O que a suite `p_09` deve validar

- Throughput sobe ao substituir o `for` sequencial por `p-limit`.
- Com CPU-bound no thread principal, a latência de `/health` degrada
  (prova do bloqueio) e **volta** ao mover para `worker_threads`.
- O processo não puxa mais jobs do que consegue processar (backpressure).

## O que observar

- Latência de `/health` sob carga (event loop bloqueado).
- Uso de heap/GC e `clinic doctor`/`flame`.
- Nº de conexões abertas no Postgres conforme a concorrência (liga com S17).
