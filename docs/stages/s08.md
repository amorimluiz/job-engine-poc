# S8 — Agendamento durável: `pg-boss`

- **Suite de testes:** `tests/p_08.spec.ts`
- **Tag:** `s08`
- **Status:** pendente

## Objetivo

Substituir o cron frágil por **agendamento apoiado no banco**, com retry e DLQ.
Cuidado central: **`singletonKey` é único entre enfileirados, não é mutex** — é
uma fonte clássica de ocorrência perdida.

## Incremento

- Trocar o agendador caseiro por `pg-boss`.
- `send('execute', payload, { startAfter, singletonKey })`.
- `retryLimit`/`retryBackoff`/`expireInSeconds`, DLQ, `batchSize`.
- Teste de corrida: agendar futuro + reenvio "agora" para o mesmo id.

## Queries prováveis (API do pg-boss; por baixo, tabelas `pgboss.*`)

```ts
// agendar para o futuro, sem colidir com ocorrências distintas
await boss.send('execute', payload, { startAfter: 60, singletonKey: pipelineId });

// com retry e expiração
await boss.send('execute', payload, {
  startAfter: 60,
  singletonKey: `${pipelineId}:${runAtIso}`, // chave distinta por ocorrência
  retryLimit: 3,
  retryBackoff: true,
  expireInSeconds: 30,
});
```

```sql
-- inspeção das tabelas internas do pg-boss
SELECT name, state, retry_count, start_after FROM pgboss.job
WHERE name = 'execute' ORDER BY created_on DESC LIMIT 10;
```

## O que a suite `p_08` deve validar

- Ocorrência futura dispara no horário (`startAfter`).
- Com `singletonKey` mal usado, a ocorrência nova é **engolida** (reproduz o bug).
- Com a chave certa (distinta por ocorrência), **não perde**.
- Falha transitória respeita `retryBackoff`; estouro vai para DLQ.

## O que observar no banco

- `pgboss.job` (estado, `retry_count`, `start_after`, `singleton_key`).
- Crescimento da tabela e necessidade de archive/retenção.
- `pollingInterval` vs `LISTEN/NOTIFY` (latência do agendamento).
