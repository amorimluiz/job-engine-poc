# S5 — MVCC, vacuum, bloat e HOT updates

- **Suite de testes:** `tests/p_05.spec.ts`
- **Tag:** `s05`
- **Status:** pendente

## Objetivo

Manter a tabela saudável sob **updates frequentes de `status`**. O Postgres não
sobrescreve a linha: cria nova versão e deixa dead tuples que o vacuum precisa
recolher.

## Incremento

- Cenário de `UPDATE job SET status = ...` em massa.
- Medir tamanho de tabela/índice e `n_dead_tup`.
- Recriar a tabela com `fillfactor = 80` e comparar (HOT updates).

## Queries prováveis

```sql
-- padrão quente do motor: transição de status
UPDATE job SET status = 'running', updated_at = now() WHERE id = $1;
UPDATE job SET status = 'succeeded', updated_at = now() WHERE id = $1;

-- medir dead tuples e vacuum
SELECT relname, n_live_tup, n_dead_tup, last_vacuum, last_autovacuum
FROM pg_stat_user_tables WHERE relname = 'job';

VACUUM (VERBOSE, ANALYZE) job;

-- tamanho de tabela e índice
SELECT pg_size_pretty(pg_relation_size('job')) AS table_size,
       pg_size_pretty(pg_indexes_size('job')) AS index_size;

-- fillfactor (recriar a tabela com espaço para HOT)
ALTER TABLE job SET (fillfactor = 80);
-- (requer reescrita: VACUUM FULL ou recriar)
```

## O que a suite `p_05` deve validar

- Após o cenário de updates, `n_dead_tup` sobe.
- `VACUUM` reduz dead tuples.
- Com `fillfactor=80`, updates que **não** mudam coluna indexada viram HOT
  (`pg_stat_user_tables.n_tup_hot_upd` > 0).

## O que observar no banco

- `pg_stat_user_tables`: `n_dead_tup`, `n_tup_hot_upd`, `last_autovacuum`.
- Tamanho da tabela/índice antes/depois (`pg_relation_size`, `pg_indexes_size`).
- Bloat: `pgstattuple` (extensão) ou comparar `pg_relation_size` com `reltuples`.
