# S1 — Modelagem e seed

- **Suite de testes:** `tests/p_01.spec.ts`
- **Tag:** `s01`
- **Status:** concluído

## Objetivo

Modelar as tabelas do motor e popular volume real (1M+ jobs) para **sentir o
custo sem índice**. A lição central: no Postgres, declarar uma FK **não cria
índice** — quem indexa é você.

## Incremento

- `pipeline(id, payload jsonb, created_at, updated_at)` — `payload` = linha do
  CSV **NYC 311**.
- `job(id, pipeline_id FK, step, status, run_at, attempts, locked_until,
  locked_by, created_at, updated_at)` — 3 steps por pipeline
  (`normalize`, `enrich`, `classify`).
- `execution(id, job_id FK, status, output jsonb, started_at, finished_at)`.
- `seed.ts` insere **340.000 pipelines** e **1.020.000 jobs** (3 por pipeline).
- **Nenhum índice secundário** (só as PKs).

## Queries prováveis

Estas são as consultas que o motor vai usar nas etapas seguintes. Sem índice,
todas fazem **Seq Scan**.

```sql
-- 1) jobs de uma pipeline (usada na listagem/detalhe)
SELECT * FROM job WHERE pipeline_id = $1;

-- 2) jobs pendentes prontos para rodar (base do claim/scheduler)
SELECT * FROM job
WHERE status = 'pending' AND run_at <= now()
ORDER BY run_at
LIMIT 10;

-- 3) histórico de execuções de um job
SELECT * FROM execution WHERE job_id = $1 ORDER BY started_at DESC;

-- 4) os 3 steps de uma pipeline, na ordem
SELECT step, status FROM job WHERE pipeline_id = $1;

-- 5) contagem para o health/observabilidade
SELECT count(*) FROM job WHERE status = 'pending';
```

## O que a suite `p_01` valida

- Tabelas `pipeline`, `job`, `execution` existem.
- `job` tem `step` e **não** tem `priority`.
- FKs corretas: `job.pipeline_id → pipeline.id`, `execution.job_id → job.id`.
- **Só PKs** (`PK_pipeline`, `PK_job`, `PK_execution`), nenhum índice secundário.
- 340k pipelines / 1.02M jobs / 3 steps por pipeline.
- `pipeline.payload` é jsonb e está preenchido.
- FK íntegra (sem jobs órfãos).
- `EXPLAIN` da query (1) é **Seq Scan**.

## O que observar no banco

Rode `bench.ts` e olhe `EXPLAIN (ANALYZE, BUFFERS)`:

- `Seq Scan on job` com `Buffers: shared read=...` alto nas queries 1, 2 e 4.
- A query 2 ainda adiciona `Sort` (não há índice em `run_at`).
- A query 3 em `execution` também é Seq Scan.

Esse é o **baseline** que o S2 vai atacar.
